# نظام طلبات الصرف — مجموعة الذيابي (نسخة Supabase)

تطبيق ويب كامل لإدارة طلبات الصرف وتتبعها عبر 6 مراحل اعتماد متتالية، مبني على
**Supabase** (قاعدة بيانات Postgres + تسجيل دخول + تخزين ملفات) بدلًا من
Firebase — **بدون الحاجة لأي بطاقة ائتمان أو بيانات دفع على الإطلاق**.

لا حاجة لأي خادم أو Backend منفصل — الملف `index.html` يحتوي على التطبيق بالكامل
(واجهة + منطق) ويتصل مباشرة بـ Supabase من المتصفح.

---

## 1. ليه Supabase بدل Firebase؟

- **مجاني فعليًا وبدون بطاقة:** الخطة المجانية لا تطلب أي وسيلة دفع إطلاقًا،
  على عكس Firebase اللي بقت تطلب ترقية لخطة Blaze (وربط بطاقة) حتى لخدمة
  Storage البسيطة.
- **مساحة محترمة لحجم فريقك:** 500 ميجا قاعدة بيانات + **1 جيجا تخزين ملفات**
  + 50,000 مستخدم نشط شهريًا + 5 جيجا نقل بيانات — أكتر بكتير من احتياج نظام
  داخلي لـ 5 مستخدمين.
- **كل حاجة في مكان واحد:** قاعدة بيانات Postgres حقيقية + Authentication +
  Storage + لوحة تحكم بصرية (Table Editor) لتعديل البيانات بدون أكواد.
- **ملحوظة واحدة يجب معرفتها:** أي مشروع مجاني يتوقف تلقائيًا (Pause) لو
  محدش استخدمه لمدة **7 أيام متواصلة**. الحل بسيط: افتح لوحة Supabase ودوس
  **Restore/Resume project** وهيرجع يشتغل خلال ثوانٍ — لا يوجد فقدان لأي بيانات.
  لو حابب تتجنب الإيقاف تمامًا، تقدر تستخدم خدمة مجانية زي
  [cron-job.org](https://cron-job.org) لعمل طلب بسيط للمشروع كل يومين.

---

## 2. ماذا يفعل التطبيق

- **إدخال طلب صرف جديد** بنفس حقول الشيت المرسل بالضبط: التاريخ، طريقة
  السداد، الجهة، الغرض، المبلغ، حالة الصرف، ملاحظات — بالإضافة إلى **إرفاق
  ملفات** وتسجيل **تاريخ الرفع** ومقدّم الطلب تلقائيًا. **رقم الطلب (م) تلقائي
  ومتسلسل بالكامل** (تولّده قاعدة البيانات نفسها، بدون أي إدخال يدوي واحتمال
  تكرار أو أخطاء ترقيم). متاح فقط لدور **موظف الحسابات**.
- **سير اعتماد بـ 6 مراحل (دورة كاملة)** لا يمكن تجاوز أي مرحلة منها:
  1. موظف الحسابات — يرفق الطلب والمرفقات ويوقّع (تلقائيًا عند الإنشاء)
  2. رئيس الحسابات — يوقّع ويكتب تعليقًا
  3. المدير المالي — يوقّع ويكتب تعليقًا
  4. المدير العام — يوقّع ويكتب تعليقًا
  5. مسؤول البنوك — يوقّع **وينفّذ الصرف فعليًا** (يحدّث حالة الصرف)
  6. موظف الحسابات (مرة أخرى) — يستلم الطلب بعد التنفيذ ويقوم **بأرشفته**
- **تعليقات لكل مرحلة** يراها الجميع، مع سجل كامل بالوقت والتاريخ.
- **لوحة مؤشرات (KPI)** موحّدة: إجمالي الطلبات والمبالغ، المؤرشفة، المرفوضة،
  قيد الاعتماد (مقسّمة حسب كل مرحلة)، تم الصرف / لم يتم الصرف.
- **فلاتر شاملة** + **تصدير Excel** بنفس أعمدة الشيت الأصلي + حالة الاعتماد
  المحدثة + ملاحظات كل مرحلة على حدة.
- **تحديث البيانات:** بما أن الاتصال بـ Supabase هنا بسيط (بدون اشتراك
  Realtime لتقليل نقاط التعقيد)، تُحدَّث الشاشة تلقائيًا كل 20 ثانية، وفور
  أي إجراء يقوم به المستخدم نفسه، مع زر **"↻ تحديث"** يدوي فوق الجدول.

## 4. إعداد مشروع Supabase (مرة واحدة فقط)

1. ادخل على https://supabase.com وسجّل حساب مجاني (بريد إلكتروني بس، بدون بطاقة).
2. دوس **New project**:
   - اختر اسم للمشروع، مثلًا `deyabi-disbursement`.
   - اختر كلمة مرور لقاعدة البيانات (احفظها في مكان آمن).
   - اختر أقرب منطقة (Region) متاحة، مثلًا `Central EU (Frankfurt)`.
   - دوس **Create new project** واستنى دقيقة أو اتنين لحد ما يتجهز.

### تشغيل سكريبت الإعداد
1. من القائمة الجانبية، ادخل **SQL Editor**.
2. دوس **New query**.
3. افتح ملف `supabase-setup.sql` المرفق، انسخ محتواه بالكامل، والصقه في المحرر.
4. دوس **Run** (أو `Ctrl+Enter`).
5. المفروض تشوف رسالة نجاح (Success. No rows returned) — ده معناه إن الجداول
   والصلاحيات والتخزين اتعملوا كلهم دفعة واحدة.

### جلب إعدادات الاتصال
1. من القائمة الجانبية، ادخل ⚙️ **Project Settings → API**.
2. هتلاقي:
   - **Project URL** (شكله `https://xxxxxxxxxxxx.supabase.co`)
   - **anon public** key (مفتاح طويل تحت قسم Project API keys)
3. افتح `index.html` وابحث عن هذا الجزء بالقرب من أول وسم `<script>` السفلي:
```js
const SUPABASE_URL = "https://YOUR_PROJECT_REF.supabase.co";
const SUPABASE_ANON_KEY = "YOUR_ANON_PUBLIC_KEY";
```
   واستبدل القيمتين بالقيم الحقيقية من مشروعك.

> **ملاحظة أمان:** مفتاح `anon public` مصمَّم عمدًا ليكون قابلًا للنشر داخل
> كود الواجهة (مش سري زي مفتاح `service_role`) — الحماية الفعلية تأتي من
> سياسات RLS (Row Level Security) المكتوبة في `supabase-setup.sql`.

## 5. إنشاء المستخدمين الخمسة (والأدوار)

النظام **لا يحتوي على تسجيل حساب جديد من الواجهة** بشكل مقصود. يتم إنشاء
المستخدمين يدويًا من لوحة Supabase:

### أ) إنشاء الحساب
1. من القائمة الجانبية: **Authentication → Users**.
2. دوس **Add user → Create new user**.
3. أدخل البريد الإلكتروني وكلمة المرور.
4. فعّل **Auto Confirm User** (عشان الحساب يشتغل فورًا بدون تأكيد بريد).
5. دوس **Create user**.

بمجرد إنشاء الحساب، **يتولّد تلقائيًا صف فارغ له في جدول `profiles`** (بفضل
الـ trigger الموجود في سكريبت الإعداد) — مفيش حاجة تعملها يدويًا هنا غير
تحديد الدور في الخطوة الجاية.

### ب) تحديد الدور والاسم
1. من القائمة الجانبية: **Table Editor → profiles**.
2. هتلاقي صف جديد ظهر تلقائيًا بمجرد إنشاء المستخدم، فيه `id` و`email`
   متعبّيين، و`role` فاضي (null).
3. دوس على خلية `name` واكتب اسم الشخص، مثلًا "عبدالوهاب المحاسب".
4. دوس على خلية `role` واكتب واحدة من القيم التالية **بالضبط**:

| الدور في الواجهة | قيمة `role` بالضبط | يتصرف في المرحلة |
|---|---|---|
| موظف الحسابات | `accountant` | 1 (تقديم — تلقائي) و 6 (أرشفة) |
| رئيس الحسابات | `accounts_manager` | 2 |
| المدير المالي | `finance_manager` | 3 |
| المدير العام | `general_manager` | 4 |
| مسؤول البنوك | `bank_officer` | 5 (تنفيذ الصرف) |

5. اضغط خارج الخلية لحفظ التعديل تلقائيًا.

كرر (أ) و(ب) للمستخدمين الخمسة كلهم.

## 6. النشر (Hosting)

بما إن Supabase بيتولى قاعدة البيانات والتسجيل والتخزين، الملف `index.html`
مجرد صفحة ويب ثابتة — تقدر تستضيفها مجانًا وبدون بطاقة على أي من:

### الأسهل: GitHub Pages (بما إنك بالفعل بتستخدم GitHub)
1. ارفع محتويات المجلد لمستودع (Repository) على GitHub.
2. من صفحة المستودع: **Settings → Pages**.
3. تحت **Build and deployment → Source** اختار **Deploy from a branch**.
4. اختار الفرع `main` والمجلد `/ (root)` → **Save**.
5. بعد دقيقة أو اتنين، هيديك GitHub رابط مباشر (شكله
   `https://username.github.io/repo-name/`) — شارك الرابط ده مع فريقك.

أي `git push` جديد للفرع `main` هيحدّث الموقع المنشور تلقائيًا، بدون أي إعداد
إضافي أو أكواد نشر (Actions) مطلوبة.

### بدائل أخرى (لو حبيت)
- **Netlify** أو **Vercel** (خطة مجانية بدون بطاقة) — اسحب وأفلت المجلد مباشرة
  من لوحة التحكم بتاعتهم.

## 7. طريقة الاستخدام

- **تسجيل الدخول**: كل مستخدم يدخل ببريده وكلمة المرور، ويظهر دوره كوسام
  بجانب اسمه أعلى الصفحة.
- **إضافة طلب صرف**: زر "طلب صرف جديد" العائم — يظهر فقط لدور موظف الحسابات.
  عند الإرسال يُسجَّل توقيعه على المرحلة الأولى تلقائيًا، وينتقل الطلب فورًا
  لانتظار رئيس الحسابات.
- **الاعتماد/الرفض**: تظهر الأدوات المناسبة لكل مرحلة (اعتماد/رفض عادي،
  أو تنفيذ الصرف لمسؤول البنوك، أو الأرشفة لموظف الحسابات في النهاية).
- **لوحة المؤشرات والفلاتر والتصدير**: تعمل بنفس الطريقة لكل المستخدمين.

## 8. ملاحظات أمنية ومقترحات تطوير مستقبلية

- سياسات RLS الحالية تسمح لأي مستخدم مسجّل دخول بتحديث أي طلب — التحقق من
  "هل دوره يطابق المرحلة الحالية؟" يتم **داخل واجهة التطبيق فقط**. مناسب
  لفريق داخلي صغير وموثوق. للحماية الإضافية لاحقًا: انقل منطق القرار إلى
  **Supabase Edge Function** ثم شدّد سياسة update.
- ملفات المرفقات في bucket خاص (private) — يتم توليد رابط مؤقت (Signed URL،
  صالح لمدة ساعة) عند فتح كل طلب، فلا يمكن لأي شخص خارج النظام الوصول للملفات
  مباشرة.
- يمكن إضافة **إشعارات بريد إلكتروني** تلقائية عبر Supabase Edge Functions.
- يمكن إضافة إمكانية "إعادة فتح" طلب مرفوض بعد التعديل وإرساله من جديد.
- لو احتجت لاحقًا تحديثات لحظية فورية (Realtime) بدل التحديث كل 20 ثانية،
  Supabase بيدعمها بسهولة (`supabase.channel(...).on('postgres_changes', ...)`)
  بعد تفعيل الـ Replication على جدول `requests` من **Database → Replication**.
